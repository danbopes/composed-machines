Factorio modding proposal

Composed Machines

Factorio 2.1 is the last major release. After it, the modding scene carries the game. Today a modder who wants a building the engine has no type for glues hidden entities together with Lua loops. The result cannot be wired, opened, blueprinted or read like a real building, and it costs UPS on top. This proposes one new entity type built from parts the engine already has, fixed at load time, that ticks only when it must. Viable, measured, about one developer-season for v1, and a path to buildings no mod can ship today.

Revision 5, 3 November 2026, against Factorio 2.1.24. Specification, writeup, benchmarks, cost model, reference mod and research: github.com/danbopes/composed-machines.

1The problem, in plain words

Factorio mods can only use the entity types that ship with the game: chest, furnace, assembler, inserter, and so on. Each type is a fixed C++ class with a fixed set of parts. A chest has one inventory and nothing else. A furnace has an input, an output, a fuel slot, modules and a progress bar, but it also insists on running real recipes.

When a modder wants something in between, say a chest that burns fuel, or a machine whose crafting rules live in Lua, there is no type for it. So they fake it. The pattern is the same across the whole modding scene: pick the nearest real type as a shell, stack invisible extra entities on top of it for the missing parts, and run a Lua loop every few ticks to make the pieces behave as one object.

One building, two ways: the Pyanodons dig site

The dig site is a creature-powered miner: feed it, give it a digosaurus, and it brings back ore from the patches around it. Read from the mod's own source (pyalienlife 3.1.8), this is what ships:

  • An assembling machine with a fake recipe it is never allowed to run, kept disabled by script forever, used only for its power buffer, its four module slots (reused as creature slots), its output slot, its trash slot and its window.
  • A hidden, unselectable chest on the same tile that holds the food.
  • For every trip, a spawned unit told to attack an invisible target; the callback when it arrives is the timer.
  • A Lua loop every 61 ticks over every dig site that checks power, food, creatures and output, draws a floating warning icon when something is wrong, eats a food, spawns the next trip, and writes the production statistics by hand.
  • A mod-built pane docked beside the vanilla window with its own food slots, including a re-implemented cursor swap and reach check. 409 lines of control script in all.

As a composed machine the whole rig is one prototype and one event handler:

{ type = "composed-machine", name = "dino-dig-site",
  energy_source = { type = "burner", fuel_categories = {"dino-food"},
                    fuel_inventory_size = 2 },        -- food value = fuel value
  energy_usage = "100kW",
  module_slots = 4, allowed_module_categories = {"digosaurus"},
  inventories = { {name = "ore",   role = "output", size = 4},
                  {name = "trash", role = "trash",  size = 1} },
  process = { cycle_time = 20 },                      -- one trip
  conditions = { {type = "module_slot_filled", count = 1, status = "no_modules"},
                 {type = "inventory_below", inventory = "ore", max_count = 1000,
                  status = "full_output"} },
  circuit_connector = {...}, circuit_outputs = "contents",
  events = { cycle_finished = true } }
-- control.lua: on cycle_finished, pick a patch in range, deplete it, insert the ore.

The research sweep behind this proposal catalogued 41 shipped compound entities built this way across the local mod library and the nine Pyanodons mods, 86 forum threads asking for the missing parts, and a 23,000-line library (0-things) that exists only to keep hidden parts alive through blueprints, undo and cloning. The same complaint has been filed since 2015. Two of the smaller items, a food slot that accepts several foods and a status that says "no creature", are open bugs on the dig site itself that the mod's authors have called API limitations.

And what the fake costs on top

The table is the argument; UPS is the bill. The chart is measured in the real engine, on a Ryzen 9800X3D: each test entity built the way mods build it today, next to the plain native entity that holds the same parts. Where the rig polls, the gap is large; where it already runs on events (the dig site, the derrick) it is small, and that is the point: those buildings are not slow, they are crippled.

2What modders asked for, and what Wube said

86 forum threads in the modding sections were catalogued, 65 of them read in full, including the first seven pages of the "Won't implement" subforum, plus 30 modding-help threads whose answer was "build a compound entity". The GitHub trackers of the mods themselves were swept separately.

The pattern on the forums

  • 13 capability gaps, ranked by how often they recur; the composed machine closes ten.
  • Of 29 "Won't implement" verdicts on machine parts: 12 cite performance, 11 "it doesn't work that way", 3 maintenance, 5 give no reason.
  • 25 threads describe a hidden-entity workaround in use; 13 say per-tick polling is the only option and call it expensive; 4 are features actually cut.
  • Two refusals were later reversed: an energy source on offshore pumps (refused 2020, shipped 2.0) and a per-entity runtime effect (hidden beacons until local_effect shipped in 2.1.13).

Features dropped or crippled

  • Better Belt Balancer (2026) compiled balancers into hidden belts so "the steady state runs no Lua at all"; a 2.1 check broke it and the feature was removed.
  • A heat-beacon mechanic (2024) rolled back after Rseding91 refused beacons with other energy kinds.
  • RealisticReactors keeps 250 reactor prototypes and swaps the building to change its power.
  • Electric locomotives, custom thrusters, a nutrient-powered roboport: not built; "there is no way".

Eleven years, in order

  • 2014A "powered up / powered down" event. no reply Mods still iterate a list every tick to notice.
  • 2015"Make the API less rigid": mix and match inventories, power, fluid. Rseding91: won't implement "Object oriented C++ doesn't lend itself well to mix and match"; Klonan points at Kerbal Space Program's part modules.
  • 2016–2018An entity component system, three times. Rseding91: never "such a system will never exist and perform the same or better than the static model". Then, 2018: "I've yet to see anyone write up how such an entity would work."
  • 2018A burner that burns constantly. won't implement "they can't sleep and that's not going to happen."
  • 2020Energy source on offshore pumps. won't implement "no interest in making or even supporting modding of offshore pumps requiring power of any kind."
  • 2020Mining recipes and an on-mined event. won't implement "Firing events has a performance impact even if zero mods are listening."
  • 2.0, 2024Offshore pumps take an energy source. Ammo turrets too. shipped
  • 2024, 2026Beacons with heat, fluid or burner energy. won't implement "huge performance overhead every time the amount of energy they have changes."
  • 2.1.12, Jul 2026raise_on_crafted: an opt-in, per-recipe event. Moshine and Muluna deleted polling loops for it. shipped
  • 2.1.13, Aug 2026local_effect: a runtime per-entity effect. Replaces a hidden beacon per machine. shipped
  • Jun 2026A spoil-time multiplier on containers. boskid: won't implement "Design decisions around spoilable items make features like this not possible."
  • Aug 2026Better Belt Balancer removes its compiled-belt feature after a 2.1 check breaks it. "no priority because of complexity" "if this API is ever implemented, I will restore the original functionality."

The shape of it: each "no" is about a vanilla type growing a part, or an event firing globally. Each "yes" is an opt-in on one prototype. This proposal is built entirely from the second kind.

3The idea

Add one entity type whose parts are chosen when the mod loads, from a short list of parts the engine already owns: inventories, an energy source (burner, electric, fluid, heat), fluid boxes, a progress timer, module slots, a circuit connector. The mod writes a prototype like any other; the engine builds the object. No Lua runs inside the machine's tick. The ice box becomes this, with no control-stage code at all:

{
  type = "composed-machine", name = "ice-box",
  inventories = {{ name = "main", size = 16, role = "storage",
                   spoil_multiplier = 8 }},   -- spoils 8x slower while fuelled
  energy_source = { type = "burner", fuel_categories = {"dry-ice"} },
  activity = "inventory_not_empty",           -- burns only while holding items
}

Three rules make it cheap:

  1. Parts are fixed at load. The engine knows every machine's shape before the first tick, so there is nothing to look up while the game runs. The loader sorts prototypes into four shapes (passive store, watcher, timer, machine), and each shape is its own compiled class.
  2. It ticks only if a part needs to. A composed chest with no burner and no timer is never put on the update list, exactly like a normal chest. A machine that has finished its work goes to sleep until an inserter wakes it, exactly like a furnace.
  3. Lua gets events, not a heartbeat. A mod opts into "cycle finished", "inventory changed", "power state changed" and so on, per prototype. This copies a hook Wube already added in 2.1.12 for recipes. There is no per-tick callback.

Why this is not the thing Wube already said no to

In 2018 a forum thread asked for a full entity component system: entities built from interchangeable behaviour components, assembled and dispatched at runtime. Rseding91 rejected it on performance grounds and has repeated the rejection since. He also left a door open:

"I'm not against that concept but I've yet to see anyone write up how such an entity would work. If someone did that it would go a long way towards me thinking about adding it to the game."Rseding91, Factorio forums, 23 June 2018, "Divorcing behavior from entities"

The difference is when the composition happens. A runtime component system decides what an entity is on every tick. This proposal decides it once, at load, and compiles the result into ordinary static classes that sit in the engine's existing per-type update buckets. The engine already works this way for one part: a furnace's energy source kind (burner, electric, fluid, heat) is picked when the prototype loads and never again. This extends that from one part to eight.

4What it looks like to write one

Eight designs taken from the forum and GitHub asks, written as the prototype a modder would ship. Each card says how the same building is faked today, what that fake cannot do however much Lua is spent on it, and, last, what the fake costs per tick next to the native parts. The lab mod builds every one as today's fake and the harness measures it (2000 instances, 3600 ticks, pinned to 4 cores).

Dig site

v1 · S3 · Pyanodons
{ type = "composed-machine", name = "dino-dig-site",
  energy_source = { type = "burner", fuel_categories = {"dino-food"},
                    fuel_inventory_size = 2 },
  energy_usage = "100kW",
  module_slots = 4, allowed_module_categories = {"digosaurus"},
  inventories = { {name = "ore",   role = "output", size = 4},
                  {name = "trash", role = "trash",  size = 1} },
  process = { cycle_time = 20 },
  conditions = { {type = "module_slot_filled", count = 1, status = "no_modules"},
                 {type = "inventory_below", inventory = "ore", max_count = 1000,
                  status = "full_output"} },
  circuit_connector = {...}, circuit_outputs = "contents",
  events = { cycle_finished = true } }
Today: an assembler shell kept disabled forever, a hidden chest for food, a unit and an invisible target per trip, a loop every 61 ticks, and a mod-drawn pane for the food slots. 409 lines of control script. Since 2.1.12 a burner assembler running a real token recipe with raise_on_crafted could carry the food as fuel and raise the finish event; the creature slots, the yield rule and the status would still be faked around it.
The rig cannot:
  • put the food on a wire: the shell's slots are empty and the chest is unselectable;
  • treat food as fuel: no fuel bar, no "no fuel" status, no inserter top-up rule, no robot delivery to a ghost;
  • report its status when it changes: a floating icon redrawn every 61 ticks, a text computed when you hover;
  • show one window: the food slots live in a docked pane with their own cursor and reach code.
Measured: 60 ns per instance per tick as the fake, 47 ns as an electric furnace (1.3x); 1.4 ns of it is script. The handler already runs on events, so the gap is small. What the dig site lacks is the table in section 1, not nanoseconds.

Cold box

v1 · S1 · Corrundum
{ type = "composed-machine", name = "ice-box",
  inventories = { {name = "cold", role = "storage", size = 16, with_bar = true,
                   spoil_modifier = {multiplier = 8, requires_power = true}} },
  energy_source = { type = "electric", usage_priority = "secondary-input" },
  energy_usage = "10kW", activity = "inventory_not_empty", tick_interval = 60,
  conditions = { {type = "powered", status = "no_power", diode = "red"} },
  events = { power_state_changed = true } }
Today: a plain chest, and every 53 ticks a loop over every box on every planet pulling each stack's spoil timer back toward a target. A spoil multiplier on containers was refused twice: "Design decisions around spoilable items make features like this not possible."
The rig cannot:
  • be powered: a chest has no energy source, so "no power" is not a status it can show, and the hidden interface is a separate consumer in the power graph;
  • catch a stack leaving: taken out by hand or by an inserter between loops, it keeps its slowed timer (there is no container transfer event);
  • freeze smoothly: the timer moves in 53-tick steps, and the author settled for "increase slowly up to 50%".
Measured: 542 ns as the fake, 16 ns as an iron chest plus a 10 kW interface (35x). The largest gap in the set, and the most-asked building.

Hearth

v1 · S3
{ type = "composed-machine", name = "hearth",
  energy_source = { type = "burner", fuel_categories = {"chemical"} },
  energy_usage = "90kW", activity = "always",
  inventories = { {name="in",  role="input",  size=1, filters={"iron-ore"}},
                  {name="out", role="output", size=1} },
  process = { cycle_time = 3.2,
    ingredients = {{type="item", name="iron-ore",   amount=1}},
    products    = {{type="item", name="iron-plate", amount=1}} },
  events = { power_state_changed = true } }
Today: an assembler with a fake recipe, a hidden reactor under it, and a loop every 20 ticks reading the reactor's temperature to zero the crafting progress when it goes cold. Asked in 2018 ("that's not going to happen") and 2023 ("the usual invisible entity contraption is the only solution").
The rig cannot:
  • stop when the fuel is taken out: it keeps crafting until the next poll (a deliberate test failure);
  • look lit: the flame, flicker and smoke belong to the hidden reactor, so the hearth looks cold while it burns;
  • take fuel like a burner: the fuel door is a proxy, which inserters fill to a whole stack.
Measured: 234 ns as the fake, 101 ns as a stone furnace plus a bare reactor (2.3x); 54 ns as a plain stone furnace (4.3x). The 20-tick temperature check is 125 ns of the fake.

Brazier

v1 · S1
{ type = "composed-machine", name = "brazier",
  energy_source = { type = "burner", fuel_categories = {"chemical"},
                    light_flicker = { color = {1, 0.6, 0.2} } },

Creep collector

v1 · S3, script start
{ type = "composed-machine", name = "creep-collector",
  energy_source = { type = "electric", usage_priority = "secondary-input",
                    drain = "5kW" },
  energy_usage = "400kW",
  inventories = { {name = "spoils", role = "output", size = 4} },
  process = { cycle_time = 2, start = "script", consume_at = "script" },
  events = { cycle_finished = true },
  conditions = { {type = "inventory_below", inventory = "spoils",
                  max_count = 200, status = "full_output",
                  diode = "yellow"} } }
Today: Rampant dropped this building: "Factorio API doesn't allow to manage energy consumption directly." The best fake is a disabled assembler with an empty recipe; the usual one is an energy interface polled every 60 ticks.
The rig cannot:
  • spend energy per unit of script-chosen work: a shell draws its recipe's power or nothing;
  • wait for the script: a recipe with no ingredients restarts the tick it ends, before Lua can gate it;
  • keep Lua out of the entity update: the harvest handler runs inside the crafted event.
Measured: 390 ns as the fake, 49 ns as an electric furnace (7.9x). The Rampant-style energy interface polled every 60 ticks costs 194 ns, half the fake. The harvest handler's 355 ns land in the assembler column, not in scriptUpdate (7 ns).

Tuned furnace

v2 · circuit input
{ type = "composed-machine", name = "tuned-furnace",
  energy_source = { type = "electric", usage_priority = "secondary-input" },
  energy_usage = "200kW",
  process = { cycle_time = 3.2, ingredients = {...}, products = {...} },
  effect_receiver = { speed_limits = {low = -0.8, high = 3} },
  settings = { {name = "rate", type = "uint32", default = 10,
                min = 1, max = 40} },
  circuit_inputs = { enable_disable = true,
                     settings = {{setting = "rate", signal = "signal-R"}} } }
Today: poll the wire every 30 ticks and write local_effect (2.1.13), or, before that, swap a hidden beacon's modules. RealisticReactors keeps 250 prototypes to change one number.
The rig cannot:
  • see a pulse: a signal shorter than the 30-tick poll is missed (a deliberate test failure);
  • stop polling: the loop runs forever, wired or not;
  • carry the setting: a value kept in script storage is not a blueprint parameter and does not survive undo by itself.
Measured: 143 ns as the fake, 74 ns with local_effect written once and no poll (1.9x); the pre-2.1.13 hidden beacon with module swaps costs 98 ns (1.5x). The 30-tick wire poll is 67 ns of the fake.

Today: "no way to do this with the API except through complex compound entity solutions" (2024). The fake is a burner assembler plus a hidden energy interface that a handler tops up on every finished craft.
The rig cannot:
  • make energy a product: it arrives as a lump after each craft, not over the cycle;
  • block on a full buffer: the next cycle's water is already taken when the block lands (a deliberate test failure);
  • be one thing in the power graph: the hidden interface is its own producer and the shell its own consumer.
Measured: 125 ns as the fake, 158 ns as a steam engine plus a stone furnace (0.8x). The twin's steam engine does more work than the hidden energy interface; the fake's own cost over an empty world is 105 ns, 3 ns of it script.

5Is it viable? Four lines of evidence

The engine already does the hard parts

Every mechanism the design relies on is one the engine already uses for a vanilla type. None of it is guessed from code: it is what the public API, the changelogs, Wube's own descriptions of the update loop and the game's per-class benchmark timers show.

  • Being updatable is opt-in per type, and the API says so directly (LuaEntity.is_updatable, since 2.0.26): chests, proxy containers and linked containers report false and cost nothing per tick. Measured: 20,000 sleeping furnaces cost the same as 20,000 chests, which cost the same as an empty map.
  • Active entities are updated in per-type batches, which Rseding91 described in 2016 and which the benchmark's per-class timers expose column by column. A new type is one more column.
  • The engine already has an "update me every N ticks" mode: beacons and roboports "do not update every tick" (Rseding91, 2024). The design's slow watcher shapes ride on it.
  • Sleep and wake are constant-time on intrusive lists, in Rseding91's own description (forum 2016, Reddit 2023). The crafting machine the proposal copies from already sleeps on an empty input and wakes when an inserter drops one.
  • An energy source's kind is fixed at load by the prototype's type field and never changes, which is why a furnace can be burner or electric without a runtime check; and a stack's spoil tick is a writable field (LuaItemStack.spoil_tick), so a re-stamp on the way in and out is one write per stack, not a per-tick walk.

A model of the update loop agrees with Wube, and with the proposal

To separate "composition" from "runtime composition", a C++ model runs a Factorio-shaped tick (inserters moving real item stacks, machines drawing from shared power networks, burners eating fuel) four ways on identical work, with identical final checksums.

The model was then re-run with the v2 parts that tick (an electric or heat output pushed on cycle finish, a circuit enable that puts the machine to sleep, a trigger on finish), with every update list shuffled so no layout benefits from a repeating pattern. Keeping the four v1 shapes and testing the energy output behind one pointer only at the push ran at 0.95 to 1.02 of hand-written classes. Multiplying into six machine shapes with no test at all ran at 0.96 to 1.01, so it buys nothing. The pointer-checked single class (variant B) did fall behind again at a million entities, 1.08 to 1.12, because its chest grows to 112 bytes. One trap turned up that is worth telling Wube: if a template gives each shape its own copy of the accessors inserters call, the inserters' calls go polymorphic and the tick slows by 12 to 35 percent; those accessors belong in a core class every shape shares. Source: model/RESULTS-v2.md.

What a real Pyanodons base spends its tick on

Three of the author's own Pyanodons saves, each run with its own mod list (73 to 76 mods), 3600 ticks, three runs, pinned to four cores. The question is not how fast the base is but where the time goes: the engine's entity update against the Lua side, which is every mod's script time plus the garbage it leaves behind.

A working reference mod, with the gaps written down

To make the proposal testable before it exists, component-lab is a Lua library that takes the proposed prototype format and builds the nearest fake out of today's types and hidden parts, plus sixteen test entities: the eight of section 4 and eight more that cover the remaining parts (a fluid-holding chest, a signal chest, a fuelled chest, a timed converter, a seep derrick, a powered signal endpoint, a mass driver and a rotating storehouse). It runs through the harness on a real headless server.

Result

  • 299 tests, 288 pass, 11 fail on purpose.
  • Build, mine, clone, blueprint and destroy round-trips for every entity.
  • Two adversarial reviews found four serious bugs: two in the library's lifecycle, a storehouse turn that ignored water and ghosts, and a fuel door inserters could drain. All fixed with regression tests.

The deliberate failures

  • A wire on the dig site cannot read its food, and its status follows the parts only at the next poll.
  • A proxy container exposes its inventory both ways, so an inserter can steal food out of the dig site; a ghost's food request is never filled.
  • A polled watcher sees a transition one interval late (brazier, hearth); a pulse shorter than the poll is lost (tuned furnace).
  • An assembler cannot consume at the end of a cycle, or block on a full energy buffer.
  • A chest ghost carries no rotation, and a hidden heat interface keeps its own side when the core turns.

Those failures are the point. They are not bugs in the mod; they are engine features the fake cannot have, and the native type would have them for free. They are the harness-checked half of the table in section 1. The mod's own gap list runs longer: no engine wake-ups (so watchers poll), no coalesced inventory or status events, no sleeping at crafter cost, no per-transfer spoil stamping, no honest status without render objects.

9What this asks of Wube

  1. Read the writeup. It is the document Rseding91 asked for in 2018 (docs/WRITEUP.md): about 7,500 words, with every engine fact it relies on listed with its verification state, and a 12,000-word specification behind it (docs/SPEC.md). It answers the six objections on record one by one.
  2. Rule on three design calls the spec flags: whether Lua may make an item fresher than new (the engine's internal path can, the Lua path cannot), how slow watchers are phased on the N-tick ring, and whether a burner refuels before or after the draw.
  3. Say which of the open engine details are wrong. Eight engine details the proposal could not verify from outside are listed with fallbacks; none changes the design, but one sentence each from someone who can read the source would retire them.
  4. If the shape rule holds up, pilot v1 behind an experimental flag. The reference mod and its 299-test harness suite are a ready regression gate; the benchmark tooling measures any build against the Lua emulation on the same saves.
  5. Independently of all of the above, two one-field changes stand on their own: require_module on crafting machines (5,100 pY farms) and the quality filter on lab input (corrundum).

What is not being asked for: no runtime components, no per-tick Lua hook, no changes to belts or vanilla types, no unbounded shape list, no new energy kinds. Each of those is a thing Wube has refused before, for reasons this design accepts.

10What is still open

  • Per-mod attribution in the pY saves. The runs show the Lua share of the tick but not which mod owns it; that needs the graphical client's time-usage panel and was not done.
  • A few engine details remain unverified (which object owns the N-tick ring, and behaviour above 195 ticks). All are listed in the spec with fallbacks; none changes the design.
  • Three design calls are flagged for a decision: whether Lua may make an item fresher than new (the engine's internal path can, the Lua path cannot), how slow watchers are phased on the ring, and whether a burner refuels before or after the draw.
  • The writeup itself (plain text, about 4300 words) is the document Rseding asked for; every benchmark placeholder is now filled.
