Factorio modding proposal · one new entity type

Composed Machines

In 2018 Rseding91 wrote that he had "yet to see anyone write up how such an entity would work": a moddable entity whose parts can be shut off. This is that write-up. One new static entity type, its parts fixed when the prototype loads, compiled into one of four classes, asleep when idle, talking to Lua only through opt-in events.

Against Factorio 2.1.24. Specification, writeup, benchmarks and reference mod: github.com/danbopes/composed-machines.

1One building, two ways: the Pyanodons dig site

The dig site is a creature-powered miner: feed it, give it a digosaurus, and it brings back ore from the patches around it. Read from the mod's own source (pyalienlife 3.1.8), this is what ships today:

  • An assembling machine with a fake recipe it is never allowed to run, kept disabled by script forever, used only for its power buffer, its four module slots (reused as creature slots), its output slot, its trash slot and its window.
  • A hidden, unselectable chest on the same tile that holds the food.
  • For every trip, a spawned unit told to attack an invisible target; the callback when it arrives is the timer.
  • A Lua poll every 61 ticks over every dig site that checks power, food, creatures and output, draws a floating warning icon when something is wrong, eats a food, spawns the next trip, and writes the production statistics by hand.
  • A mod-built pane docked beside the vanilla window for the food slots. 409 lines of control script in all.

As a composed machine the whole building is one prototype and two event handlers, and it plays the same: one timer stands in for up to four parallel trips, and the yield scales with the creatures present.

{ type = "composed-machine", name = "dino-dig-site",
  energy_source = { type = "electric", usage_priority = "secondary-input" },
  energy_usage = "100kW",
  module_slots = 4, allowed_module_categories = {"digosaurus"},   -- creature slots, as pY uses them today
  inventories = { {name = "food",  role = "input",  size = 2, filters = {...}},   -- pY's food list
                  {name = "ore",   role = "output", size = 4},
                  {name = "trash", role = "trash",  size = 1} },
  process = { cycle_time = 20, consume_at = "script" },
  conditions = { {type = "module_slot_filled", count = 1, status = "no_modules"},
                 {type = "inventory_below", inventory = "ore", max_count = 1000,
                  status = "full_output"} },
  circuit_connector = {...}, circuit_outputs = "contents",
  events = { cycle_started = true, cycle_finished = true } }
-- cycle_started: eat one food, remember its yield.  cycle_finished: insert yield x filled creature slots.

Since 2.1.12 a burner assembler running a token recipe with raise_on_crafted could raise the finish event, but the food slot, the yield rule, the no-creature status and the stop-at-1000 rule would still be faked around it. The dig site's workaround already runs on events and is not slow: measured at 60 ns per instance per tick against 47 for an electric furnace. Where a building already runs on events, it is not slow, it is crippled. Section 4 says how.

2The design

Add one entity type, composed-machine, whose parts are chosen when the mod loads from a short list the engine already owns: named inventories, each with a role (input, output, storage, trash), filters and inserter rules; an energy source of any vanilla kind; fluid boxes; a process, which is a timer with optional ingredients and products and no recipe selection; module slots; a circuit connector; up to four settings; a short list of conditions that set the status; and opt-in events. The mod writes a prototype like any other, and the engine builds the object. A hearth that smelts on its own fire becomes this, with no control-stage code at all:

{ type = "composed-machine", name = "hearth",
  energy_source = { type = "burner", fuel_categories = {"chemical"} },
  energy_usage = "90kW", activity = "always",      -- burns while it has fuel, ore or not
  inventories = { {name="in",  role="input",  size=1, filters={"iron-ore"}},
                  {name="out", role="output", size=1} },
  process = { cycle_time = 3.2,
    ingredients = {{type="item", name="iron-ore",   amount=1}},
    products    = {{type="item", name="iron-plate", amount=1}} } }

Three rules make it cheap:

  1. Parts are fixed at load. The loader reads the part list once and sorts the prototype into one of four classes by which parts tick: passive (nothing ticks: a store), watcher (an energy source or a condition to check, no process), timer (a process without an energy source), machine (a process with one). Each class is compiled separately. Nothing is looked up while the game runs, and a prototype never changes class.
  2. It ticks only if a part needs to. A passive store is never on an update list, exactly like a chest. A machine that has finished its work sleeps until an inserter wakes it, exactly like a furnace.
  3. Lua gets events, not a heartbeat. A mod opts into "cycle started", "cycle finished", "inventory changed" and so on, per prototype: the same opt-in Wube added for recipes in 2.1.12 (raise_on_crafted). Delivery is new: events are queued during the entity update and raised together right after it, so no Lua runs inside the update. There is no per-tick callback.

The rest is settled in the specification, one line each here. Inserters and loaders: fuel first, then input inventories in declared order by filter, then storage; extract from outputs, then the burnt result, then trash, never from inputs or fuel (section 3.5). Status: the furnace's statuses plus the ones the conditions declare (section 5). Save and load: a part mask plus each part's own serialiser; blueprint, undo, upgrade and fast replace follow the container and crafter rules (section 9). Lua: the entity gains named-inventory access and the cycle fields; the control behaviour is the assembler's plus read_fuel (section 7). Window: the furnace window with one grid per inventory (section 8).

3Why a new type, and why it is not the ECS you refused

In 2018 a forum thread asked for a full entity component system: entities built from interchangeable behaviour components, assembled and dispatched at runtime. Rseding91 rejected it on performance grounds and has repeated the rejection since. He also left a door open:

"I'm not against that concept but I've yet to see anyone write up how such an entity would work. If someone did that it would go a long way towards me thinking about adding it to the game."Rseding91, Factorio forums, 23 June 2018, "Divorcing behavior from entities"

The difference is when the composition happens. A runtime component system decides what an entity is on every tick. This proposal decides it once, at load, and compiles the result into ordinary static classes that sit on the engine's per-type update lists. The prototype already fixes one part this way: a furnace's energy source kind is chosen at load and never changes at runtime. This proposal fixes all of them at load.

And why not more fields on the assembler or the container

Wube has added parts to existing types well: offshore pumps and loaders took an energy source, recipes took raise_on_crafted, effect receivers took local_effect. Where one field is enough, this proposal asks for the field: require_module on crafting machines and a quality filter on lab inputs are listed in section 8 as standalone asks. Four things do not fit as a field. A burner or a power condition on a container puts a ticking part on a type every chest in every save runs, the same objection Wube gave to energy on belts in 2024. A crafter without recipe selection, started by script or consuming by script, drops the invariants recipe selection guarantees. Several named inventories with their own roles, filters and inserter rules are not a field on any type. Burning on a rule other than "while crafting" (always, or while holding items) changes what a vanilla burner does. Each of these lands in code every vanilla assembler or chest runs. A separate type confines all four to prototypes that declare them, and no vanilla entity changes. If Wube would rather extend the crafter, the minimum that covers the dig site and the timed converter is start = "script", consume_at = "script", named extra inventories with roles, and a conditions list.

5How it runs in the engine

What it reuses, and what Wube would need to confirm

Every mechanism the design relies on is one the engine already uses for a vanilla type. The claims here come only from the public API, the changelogs, Wube's own descriptions of the update loop and the game's per-class benchmark timers; the writeup marks each of its assumptions, and the five that matter most are listed first in the specification's section 13.

  • Being updatable is opt-in per type, and the API says so directly (LuaEntity.is_updatable, since 2.0.26): chests, proxy containers and linked containers report false and cost nothing per tick. Measured: 20,000 sleeping furnaces cost the same as 20,000 chests, which cost the same as an empty map.
  • Active entities are updated in per-type batches, which Rseding91 described in 2016 and which the benchmark's per-class timers expose column by column. A new type is one more column.
  • Beacons and roboports "do not update every tick" (Rseding91, 2024). A composed machine that only needs a check once a second gets the same effect from a countdown on its class's list; whether a native every-N-ticks schedule can host it is a question for Wube.
  • Sleep and wake are constant-time on intrusive lists, in Rseding91's own description (forum 2016, Reddit 2023). The crafting machine the proposal copies from already sleeps on an empty input and wakes when an inserter drops one.
  • An energy source's kind is fixed when the prototype loads; a stack's spoil tick is a writable field (LuaItemStack.spoil_tick).

Composition at load costs nothing; composition at runtime costs what Rseding said

To separate the two, a C++ model runs a Factorio-shaped tick (inserters moving real item stacks, machines drawing from shared power networks, burners eating fuel) four ways on identical work, with identical final checksums. One finding is worth a line on its own: the accessors inserters call must live in a base class every shape shares, or those calls go polymorphic and the tick is 12 to 35 percent slower in the model.

What today's workarounds cost

The reference mod builds sixteen test entities the way mods build compound entities today (a shell, hidden parts and a Lua script) and the harness measures each next to the native entities that hold the same parts. In three large Pyanodons saves, all mods' Lua together is 29 to 41 percent of the tick; how much of that is compound entities was not measured.

6The objections on record, and the answers

Every past "no" on the forums was about a vanilla type growing a part, or an event firing globally. Every "yes" was an opt-in on one prototype: an energy source on offshore pumps (refused 2020, shipped in 2.0), raise_on_crafted (2.1.12), local_effect (2.1.13). This design is built only from the second kind.

Wube saidWhenThe proposal's answer
A generic mix-and-match entity "simply will never happen"; it would mean "throwing out the entirety of the code around entities"2015, 2019That describes a runtime-generic system. This is one static class per shape, decided at load. The model's runtime variant costs 2.2–2.9x; the compiled-shape variant 1.00x. The reuse map in section 8 names the new code; everything else is the furnace's and the container's own behaviour.
"Firing events has a performance impact even if zero mods are listening"2020True of a global event. These are per-prototype opt-ins, the design Wube shipped as raise_on_crafted in 2.1.12. With nobody opted in, the cost should be one flag check per finished cycle (assumed; for Wube to confirm); prototypes that never declare the flag pay nothing.
Entities that burn constantly "can't sleep and that's not going to happen"2018Agreed for vanilla types, which are untouched. A composed burner sleeps when its activity inventory is empty; an "always" burner is one modder's explicit choice on one prototype, stays on the update list like a boiler, and replaces a hidden reactor plus a Lua poll.
Beacons with other energy kinds: "huge performance overhead every time the amount of energy changes"2024, 2026Nothing in v1 touches beacons. Effect broadcast is a later, debated step, for exactly this reason.
A spoil multiplier on containers: "design decisions around spoilable items make features like this not possible"2025, Jun 2026Not in v1. Offered as a separate add-on for Wube to rule on: a re-stamp on the way into and out of one declared inventory, never a per-tick walk. Cutting it changes nothing else.
Logistic mode on a proxy container: a proxy "does not own the inventory it borrows, which means it is not instantly notified of content changes"2026This argues for the design: a composed machine owns every inventory it declares, so the transfer hook that wakes inserters and raises events is its own.

7Who needs it

Asked for on the forums since 2014 (86 threads catalogued, 65 read in full) and visible in the mods' own issue trackers (176 verified findings across 100 repositories, 30 of them a building or feature the author gave up on). v1 converts 22 of 189 surveyed scripted buildings fully and 36 partly; most of the rest need a different core (an inserter, a roboport, a train stop, a silo, a unit, a drill), which this type does not claim.

"It seems to be an API limitation. Using the API I can set a filter, but I cannot make a filter for multiple types of food. Not going to fix this."Pyanodons, dig-site food slot, 2023. A v1 filter is a list.
"Factorio API doesn't allow to manage energy consumption directly."Rampant, the reason given for dropping the creep collector. A v1 process with energy per cycle.
"Spoilage math wasn't working, and it was easier to increase slowly up to 50%."Corrundum, the ice box. The spoil add-on, two re-stamps instead of a scan.

8First step, and what this asks

  1. Start with v0, the machine shape alone. One new type that accepts only prototypes resolving to the machine class (a process plus an energy source) and the passive class, which comes free because it is constructed like a container and never updated. The machine behaves as the furnace does, with recipe selection removed: a fixed process (cycle time, ingredients, products) or a script-consumed one; one to four named inventories with roles and the drop and pickup order of the specification's section 3.5; any vanilla energy source; module slots with local_effect; the assembler's circuit reads plus read_fuel; the built-in statuses plus two conditions, module_slot_filled and inventory_below; and two opt-in events, cycle_started and cycle_finished, raised as raise_on_crafted is raised today. Its window is the furnace window with one grid per inventory, capped at 4 inventories and 256 slots. That alone covers the dig site, the hearth, the timed converter, the creep collector and the seep derrick, and it gives passive multi-inventory stores with real inserter rules. It touches no shared transfer path and no vanilla type.
  2. Rule on the shape rule. May a modded entity's parts be fixed at load and compiled into one of four classes, with events opt-in per prototype?
  3. Rule on three design calls. Event delivery queued after the update, or synchronous as raise_on_crafted is; whether a burner refuels before or after the draw; whether the spoil add-on is wanted at all, and if so whether a stack's spoil tick may pass full freshness while it sits in its inventory (a Lua write refuses that today; measured).
  4. Correct what could not be verified from outside. The engine assumptions are listed in the specification's section 13 with a fallback each. One sentence apiece settles them.
  5. Standalone, whatever the answer. require_module on crafting machines (5,100 farms in one Pyanodons save poll for it) and a quality filter on lab inputs.

Sizing is Wube's to judge. v0 above is the smallest piece that stands alone; the window is the riskiest unit. What is not being asked for: no runtime components, no per-tick Lua hook, no changes to belts or vanilla types, no new energy kinds, no unbounded shape list. One optional add-on, the spoil modifier, does touch shared code (a re-stamp on each transfer path into and out of a declared inventory) and is offered separately so it can be refused on its own.

Later, each separately: the watcher and timer classes, a per-prototype update interval, settings, conditions beyond the built-in statuses, more events. After v1: electric generation (16 surveyed buildings), heat output, circuit input. Debated: a logistic role per inventory, effect broadcast. Details: docs/V2-PARTS.md.
