# Composed machines: a writeup for Wube

*How a load-time-composed modding entity would work.*

Engine behaviour that is not publicly documented is marked 'assumed, for Wube to confirm'; every other claim cites the API or prototype reference, a changelog, a Wube developer's public post, or a measurement in this repository.

Revision 5, 2026-11-03 (history in `CHANGELOG.md`); about 7,400 words. Companions: `docs/SPEC.md` (the field-level spec the reference mod mirrors) and `docs/ENTITIES.md` with `docs/TEST-ENTITIES-2.md` (what the reference mod builds and measures). Benchmark numbers marked quiet-box come from `bench/RESULTS.md` (3600 ticks, 5 runs, CPUs 8-11 pinned). Every other number carries its source and its noise.

composed-machine is one static entity type whose parts are fixed at prototype load and reduced to four compiled classes; this document says how each part updates, sleeps, saves and reaches Lua.

On 2018-06-23 Rseding91 wrote, about a general-purpose modding entity: "I'm not against that concept but I've yet to see anyone write up how such an entity would work ... If someone did that it would go a long way towards me thinking about adding it to the game." The next day: "see if it can actually work to make such an entity where parts of it can just be shut off" (forums.factorio.com, p=367885, read in full). This is that writeup: one new static entity type whose optional parts are chosen when the prototype loads, which joins the update list only when a part has to tick, and which tells Lua about edges through opt-in events. Section 2 says why it is not the entity component system he rejected in the same thread, and section 3 why it is a new type rather than more fields on an existing one.

## 1. The design

**Prototype.** type = "composed-machine", inheriting EntityWithOwnerPrototype. Parts, each optional: up to eight named inventories with a role (input, output, storage, trash) that fixes inserter access, filters and a bar; one energy source from the full union, loaded through the same `energy_source` definition the existing types that take one use; up to eight fluid boxes; a recipe-less process whose ingredients and products are the ordinary recipe structs, started automatically or by script; module slots with an effect receiver; a circuit connector with contents or script-written logistic-section output; up to four engine-evaluated conditions, each declaring its status; up to four blueprintable scalar settings; an activity rule; a tick_interval (1 to 60); opt-in event flags. A spoil-rate modifier on one declared inventory is not part of v1: it is offered as a separately refusable add-on (`SPEC.md`, Add-on A). `SPEC.md` section 1 has the field table and the validation rules.

**Shapes.** The loader reduces the part set to one of four. S0 (passive): no process, nothing to watch per tick. S1 (watcher): no process, but a burner that must burn (a burner is assumed to refill from its fuel only during its owner's update; for Wube to confirm), a power-dependent condition, a fluid threshold or, with the add-on, a power-dependent spoil modifier. S2 (timer): a process without energy. S3 (machine): a process with energy. Each shape is a separate final class; absent parts are empty bases, not null pointers checked per tick. S0 is not updatable, like a container (`LuaEntity.is_updatable` is false for one, and 20000 chests run at the empty-world floor, `bench/RESULTS.md`), so the instance is never in any active list. S1 to S3 are three new entries in the engine's per-type update order (updatability is a side interface with per-type batched updates, Rseding91, 2016, p=154019). An instance with tick_interval above 1 updates every N ticks: the baseline is a countdown on its shape's normal update list, one compare per tick. Beacons and roboports already "do not update every tick" (Rseding91, 2024, t=113632); whether a native every-N-ticks schedule can host this type is for Wube to say.

**Updatable iff.** A prototype is updatable iff its shape is not S0. An instance is active iff it is updatable, not deactivated (script, deconstruction, frozen, control behaviour) and not asleep. It sleeps as a crafting machine does, with an O(1) unlink from the intrusive active list (Rseding91, 2016, p=154019, and on Reddit in 2023), which staff have said is safe during the update loop (FFF-204 discussion, 2017, p=303569), on exactly the results only an external action can change (a condition failed, ingredients short, output full, waiting for script, burner empty, activity inventories empty). It is registered on the same wake-up lists inserters already sleep on, and every transfer into or out of its inventories is the wake: an insert wakes what waits on output, a removal what waits on input (assumed from the engine's behaviour; for Wube to confirm). The electric network is not a wake source: an instance waiting on power stays active at zero progress, as a crafter in a brownout is assumed to (for Wube to confirm); and a sleeping electric instance still pays its `drain`, as idle vanilla machines do (20000 idle electric furnaces measure 0.15 ms per update against the chests' 0.11, `bench/RESULTS.md`). tick_interval is the lever, updating every N ticks with an electric buffer the loader sizes for N. Belts and vanilla types stay untouched (Rseding91, 2024-12-23, p=654992).

**Update.** S3's update is the crafting machine's update minus recipe selection: energy source tick (assumed, as for crafters, to be needed only for burner and fluid sources); gates; conditions and start; progress at got over need, the draw dispatching on the source's kind fixed at construction, copied from the crafter's (assumed), so low power slows the cycle; finish through the crafter's product path with productivity as bonus_progress; events queued; status and visuals; sleep decision. S2 drops the energy terms by if constexpr; S1 is the energy tick, the gates, the tick-evaluated conditions and the activity rule. Lua never runs inside any step.

**Events.** Seven, each opt-in per prototype with an id allocated at load like custom-event: cycle_started, cycle_finished, status_changed, inventory_changed, power_state_changed, fluid_threshold, settings_changed. The opt-in is the one Wube added for recipes in 2.1.12 (raise_on_crafted). Delivery is new, not a copy: events are queued during the entity update and raised together right after it, before the script phase, in update order, coalesced to one per entity per tick, so no Lua runs inside the update; a change after that point belongs to the next tick. Each queue entry holds the entity's unit number, and an entry whose entity is no longer valid when the queue is raised (destroyed, mined, or destroyed by an earlier handler in the same batch) is dropped without an event. The fallback, and the v0 choice if Wube prefers it, is to raise synchronously, exactly as raise_on_crafted does today: its handlers run inside the crafting update (measured: crafted-event handlers are billed to the AssemblingMachine column, not scriptUpdate, `bench/RESULTS.md` section b; script trigger effects are assumed to behave likewise). The engine is assumed to have no deferred queue for entity events (for Wube to confirm). The queue is preferred because a synchronous handler could destroy the entity being updated in the middle of its type's update list. No per-tick hook of any kind; no inventory copy in any payload (consume_at = "script" hands the handler the live stacks).

**GUI.** Assembled from existing widgets in a fixed order, nothing drawn for an absent part: the crafter frame and status line with the energy source's own widget, as vanilla machines show it; a slot grid per inventory (the 2.1.7 inventory element); the module row; fluid slots; settings; the circuit panel; the tooltip from each part's own description lines, as vanilla tooltips are built. Every action is a normal input action; a relative GUI anchor lets mods attach panels.

**Blueprint, undo, migration.** One entity on the engine's normal paths: blueprint carries bar, filters, circuit state, item requests and settings; undo is one stack item; mining returns every inventory; cloning copies all parts; fast replace transfers inventories by name, and from a plain container into the first storage inventory. The save stores a part mask, then each part's own serialiser; the per-prototype inventory name table goes once into the map's prototype-migration data, so a renamed inventory migrates by name and a changed shape is re-instantiated on load as the class the prototype now implies. A mod leaving a compound entity ships one migrations script: create, move by inventory, destroy the hidden parts.

## 2. Why this is not the ECS that was rejected

Rseding91 rejected runtime component systems in April 2016, June 2018 and three times in November 2018 (the 10th, 12th and 24th), and the model built for this writeup agrees with him. What he left open was one modding entity whose parts can be shut off. Shutting parts off at load, not at runtime, is what the prototype already does for one part: a furnace's energy source kind is chosen at load and never changes at runtime. The `energy_source` field picks one of five kinds (electric, burner, heat, fluid, void) at data load, and each instance keeps that kind for life (public prototype reference). The per-tick cost of that choice in a crafter is assumed to be a dispatch on the fixed kind, with real work only for burner and fluid sources (for Wube to confirm); the composed machine copies the same dispatch. This proposal fixes all of its parts at load, keeps a normal per-entity update, and adds three more entries to the engine's per-type update lists.

Mechanisms reused, by behaviour: the updatable side interface with O(1) sleep and wake on intrusive active lists (Rseding91, 2016, p=154019; 2023 on Reddit), which containers do not take part in; the per-type batched update over the active list; less-than-every-tick updates as beacons and roboports already have them, as the model for tick_interval (Rseding91, 2024, t=113632); the crafting machine's sleep and wake and the wake-up lists inserters sleep on; the five energy source kinds and their per-instance creation; the crafter's inventory access and its notification on every transfer; the effect receiver behind module slots and `LuaEntity::local_effect`; logistic sections as the constant combinator uses them; the recipe give, consume and refund paths; the crafter's energy draw; the per-prototype event ids of custom-event and raise_on_crafted; and, for the spoil add-on only, the writable spoil tick (`LuaItemStack.spoil_tick`). New code: the shape selection at load, the drop and pickup rules across several inventories (`SPEC.md` section 3.5), the condition evaluator, the event queue raised right after the entity update, the energy-draw dispatch (a copy of the crafter's), the GUI composition, and, for the add-on only, the spoil re-stamp hooks on the transfer paths. `SPEC.md` section 13 lists each fact with its verification state.

**What the model says.** `model/RESULTS.md` is one C++17 program that runs a Factorio-like tick (real inventory rules, inserters, electric networks in brownout, burners) under four architectures with identical work and a checked identical final state. A, static: one class per type, the engine today. B, composed: one class, parts as pointers or bits fixed at construction and checked per tick. C, the runtime ECS the 2018 thread asked for: a component list per entity, virtual update per component, siblings found by tag. D, the template variant: Composed<Input, Energy, Timer, Fluid>, one instantiation per part shape, absent parts as empty bases, their checks removed by if constexpr, one update list per ticking shape. On a Ryzen 9800X3D under g++ 13 and clang 18, 10 thousand to 1 million entities: B over A 1.05 to 1.10, widest at 1M where the run is memory-bound, the signature of object size (in the model, B's chest is 80 bytes against A's 16); C over A 2.2 to 2.9 and growing with N, because inserters look into their targets' components every tick; D over A 1.00 plus or minus 0.02 at every N under both compilers, the chest shape at 16 bytes like the model's static chest. So the design keeps the shape out of the object layout. D's cost is named too: each shape is one more slot in the per-type update order on every surface, and more instruction cache, which is why the shape set is four and curated. The model is not Factorio: real entities are much larger and most of a real tick is absent.

The model was then re-run with the parts beyond v1 that tick (an electric or heat output pushed on cycle finish, a circuit enable that puts the machine to sleep, a trigger on finish), with every update list shuffled so no layout benefits from a repeating pattern (`model/RESULTS-v2.md`). Keeping the four v1 shapes and testing the energy output behind one pointer only at the push ran at 0.95 to 1.02 of hand-written static classes. Multiplying into six machine shapes with one update list each and no test at all ran at 0.96 to 1.01, so it buys nothing measurable. The pointer-checked single class (variant B) fell behind again at a million entities, 1.08 to 1.12, because its chest grows to 112 bytes. So v2 keeps four shapes and a null check confined to the push step. The inserter-facing accessors belong in a base class every shape shares, or those calls go polymorphic (12 to 35 percent slower in the model at ten to a hundred thousand entities).

**What the engine says.** On the busy box at N = 2000 cells (`bench/RESULTS.notes.md`; per-class figures from `bench/results`), one working electric furnace costs 31 ns per tick in its own column (Furnace 0.0626 ms over 2000) and one working assembler 30 ns; the per-cell totals of 78 and 175 ns include two inserters and two infinity chests and are not the machine. A sleeping-furnace world and a chest world have the same entityUpdate within noise (0.00216 against 0.00219 ms at N = 200): sleeping entities are off the update list, as Wube staff have described ("they do not participate in the update loop", FFF-204 discussion, 2017, p=303569). So an S3 instance is projected at about 30 ns per working tick times D over A, and zero in entityUpdate while asleep or S0; an electric sleeper still pays its drain in the electric network update.

The quiet-box rerun (`bench/RESULTS.md`: 3600 ticks, 5 runs, the best run kept, CPUs 8-11 pinned, load average 1.5 to 3.2) measured the native matrix in ns per instance per tick over the empty world, whole update, at N = 2000 and 20000: wooden chests 2 and 0.5, the empty-world floor; idle electric furnaces at the same floor (entityUpdate 0.003 ms at both sizes, as in the empty world); a working electric furnace cell 47 and 64 ns, a stone furnace cell 55 and 61, an assembler cell 100 and 140, each cell again the machine plus two inserters and two infinity chests. The machines' own columns came out lower than on the busy box (Furnace 0.039 ms and AssemblingMachine 0.037 ms over 2000, about 20 and 19 ns each), so 30 ns per working tick is the conservative end. On mulark's public maps (credited to mulark and the map authors, not redistributed), test-000060.no_primed.400x (400x direct-insertion chains) spends 1.73 ms per tick in AssemblingMachine and 0.74 ms in Inserter of 3.95 ms per update.

Each test entity's Lua emulation next to its native comparison, same layout, N = 2000, in ns per instance per tick on the whole update, composed against native, with the composed entity's scriptUpdate share in brackets: cold box 542 against 16 (scriptUpdate 466 of the 542); timed converter 777 against an assembler cell's 100 (625); signal chest 413 against 93 (301); signal endpoint 81 against 15 (64); fluid chest 83 against 22 (59); fuelled chest 152 against 51 (94); seep derrick 149 against 90 (4); dig site 60 against an electric furnace cell's 47 (1). The cold box figure is a ceiling, not a prediction: its emulation polls every box once a second, while a native spoil add-on would re-stamp a stack once on the way in and once on the way out and scan nothing per tick. Where the hidden part is a native entity (reactor, EEI, storage tank, combinator) it costs what its native equivalent costs in its per-class column (Reactor 0.0516 against 0.0514 ms for 2000 fuelled chests), so the gap in the five non-crafters is the polls that stand in for engine wake-ups: scriptUpdate plus extra Lua GC. The two pY-style crafters, whose scripts run only on events, pay 1 to 4 ns of scriptUpdate and carry their gap in the shell's AssemblingMachine column instead (derrick shell 0.153 ms against 0.045 for its native equivalent, converter shell 0.219 against 0.037 for a gear assembler); a crafted-event handler is billed to that column, which is the likely cause. Polls that all land on one tick (timed converter, signal chest) keep the median tick near native but push p95 to 5 to 10 ms. The Lua column is the status quo's ceiling; the native type stays projected at the native comparison times D over A. Caveats: the derrick's native equivalent is a chemical plant on lubricant (1 s cycle against 2 s), and the fuelled chest's is the emulation's own hidden reactor with no script.

**Each objection, answered.** "The dynamic nature of every bit of logic every component has to do" (2018): parts are fixed at load, the class is static per shape, nothing is looked up by tag. By-type batching gave "zero difference" (2016): not claimed; D over A 1.00 means no loss, not a gain; the claim is no Lua per tick and no hidden entities. Pluggable energy sources "still don't divorce the behavior from the entity" (Nov 2018): agreed; one class handles the energy source as a crafting machine does. Energy source support "means making a given entity updatable which isn't happening for belts" (Dec 2024): new type only. "Massive drain" (2017), answered by Wube itself with raise_on_crafted in 2.1.12: the same opt-in, plus coalescing. Generic per-entity data makes every entity grow (boskid): fixed-size settings, at most 16 bytes, only on this type. A spoil multiplier "would require adjusting spoil tick every time spoilable item is moved between inventories" (boskid, 2025-08-13): the spoil add-on is exactly that cost, confined to one declared inventory of one opt-in prototype, and it is not in v1; he did not permit it. The author assumes the re-key itself is one re-stamp of the stack's spoil tick per stack per transfer, with no search and no inventory scan (for Wube to confirm). The cost he means is the hook: each transfer path would gain a check for a modified inventory.

The objections on record, and the answers. A second forum survey (`research/forum-dropped-features.md`, 53 threads not read before, 29 of them in Won't implement) collected every staff refusal that touches a part of this type. Six of them are the ones this writeup has to meet head on.

- "Make the API less rigid" (t=15257, 2015) and custom control behaviours on any prototype (t=69180, 2019): a generic mix-and-match entity "simply will never happen", would mean "throwing out the entirety of the code around entities", would perform so badly "you probably couldn't ever leave red science", and would be un-maintainable. Both describe a runtime-generic system. This type is one static class per shape, reduced at data load, with no code path that asks an entity what it is; the model's variant C is the thing refused, and it measures 2.2 to 2.9 times static, while D measures 1.00. Klonan's pointer in the 2015 thread, Kerbal Space Program's part modules, is the right picture: modules declared in the part's config, fixed when the part loads.
- "Firing events has a performance impact even if zero mods are listening" (t=88647, 2020). True of a global event. The events here are per-prototype opt-in ids, the design Wube shipped as raise_on_crafted in 2.1.12. With nobody opted in, the cost should be one flag check per finished cycle (assumed; for Wube to confirm), and nothing on prototypes that do not declare the flag.
- "Entities that don't consume power constantly ... are asleep to save CPU time. To make them consume constantly would mean they can't sleep and that's not going to happen" (t=61277, 2018, about a continuous-burn option on vanilla burners). Agreed for vanilla types, which this type does not touch. A composed machine with a burner and activity = "inventory_not_empty" sleeps when empty and burns when holding something; one with activity = "always" is a watcher that stays on the update list like a boiler, by the modder's explicit choice on one prototype, and is reported as such by the loader. The alternative modders use today, a hidden reactor under every machine plus a tick loop (t=108882), is that cost plus Lua.
- Beacons with other energy kinds (t=113632, 2024; t=132603, 2026): refused because a beacon's energy changes are expensive and beacons do not update every tick. Effect broadcast is a later part and is listed as debated for exactly this reason; nothing in v1 touches beacons.
- A spoil multiplier on containers (t=134525, 2026-06-28, boskid: "Design decisions around spoilable items make features like this not possible"), after p=678356 (2025). Not in v1. Offered as a separate add-on for Wube to rule on: a re-stamp on the way into and out of one declared inventory, never a per-tick walk. Cutting it changes nothing else. The author assumes (`SPEC.md`, Add-on A; for Wube to confirm) that the re-key is one re-stamp of a stack's spoil tick, and that the cost is the hook on each transfer path into and out of the declared inventory.
- Logistic mode on a proxy container (t=136024, 2026, boskid: a proxy "does not own the inventory it borrows, which means it is not instantly notified of content changes"). This one argues for the design: a composed machine owns every inventory it declares, so the transfer notification that wakes inserters and dirties inventory_changed is its own.

Two refusals were reversed later, which is the pattern this writeup counts on: an energy source on offshore pumps ("no interest in making or even supporting", 2020, t=81770) shipped in 2.0, and the runtime per-entity effect that hidden beacons stand in for shipped as `LuaEntity::local_effect` in 2.1.13 (t=132032), which already retires pY's 2,176 TURD beacons without this type. Of the 29 Won't-implement threads read, 12 give performance as the reason, 11 "it doesn't work that way", 3 maintenance; the design answers the first group with the shape rule and the third with a maintenance surface that is a subset of the crafting machine's.

## 3. Why a new type, and not more fields on the assembler or container

Wube has added parts to existing types well: offshore pumps and loaders took an energy source, recipes took raise_on_crafted, effect receivers took local_effect. Where one field is enough, this proposal asks for the field: require_module on crafting machines and a quality filter on lab inputs are listed below as standalone asks. Four things do not fit as a field. A burner or a power condition on a container puts a ticking part on a type every chest in every save runs, the same objection Wube gave to energy on belts (p=654992). A crafter without recipe selection, started by script or consuming by script, drops the invariants recipe selection guarantees. Several named inventories with their own roles, filters and inserter rules are not a field on any type. Burning on a rule other than "while crafting" (always, or while holding items) changes what a vanilla burner does. Each of these lands in code every vanilla assembler or chest runs. A separate type confines all four to prototypes that declare them, and no vanilla entity changes. If Wube would rather extend the crafter, the minimum that covers the dig site and the timed converter is start = script, consume_at = script, named extra inventories with roles, and a conditions list.

## 4. The problem

The research survey (`research/RESEARCH.md` section 2) counted 41 shipped compound entities; `SPEC.md` appendix A collapses 8 of them fully and 9 partly. pY's dino dig site is the typical one: an assembling machine with a fixed recipe, permanently disabled by script, plus a hidden food container, plus a unit and a target entity per trip, driven every 61 ticks. Section 5 shows it as one prototype. The mods' own GitHub trackers give 176 verified findings in 100 repositories (`research/github-issues.md`): 35 of 176 fixed by v1; 60 more by a later part.

In three large Pyanodons saves, Lua (all mods' script plus GC) is 29 to 41 percent of the tick; the per-mod split was not measured (bench/RESULTS.md section d).

The asks and the answers, in order (dated threads and quotes in `research/RESEARCH.md` and `research/forum-dropped-features.md`):

- **2014.** A "powered up / powered down" event is asked for; no reply. Mods still iterate a list every tick to notice.
- **2015.** "Make the API less rigid": mix and match inventories, power, fluid (t=15257). Rseding91, won't implement: "Object oriented C++ doesn't lend itself well to mix and match". Klonan points at Kerbal Space Program's part modules.
- **2016 to 2018.** An entity component system, asked three times. Rseding91: "such a system will never exist and perform the same or better than the static model". Then, in 2018: "I've yet to see anyone write up how such an entity would work."
- **2018.** A burner that burns constantly (t=61277). Won't implement: "they can't sleep and that's not going to happen."
- **2020.** An energy source on offshore pumps (t=81770). Won't implement: "no interest in making or even supporting modding of offshore pumps requiring power of any kind."
- **2020.** Mining recipes and an on-mined event (t=88647). Won't implement: "Firing events has a performance impact even if zero mods are listening."
- **2024, 2.0.** Offshore pumps take an energy source; ammo turrets too. Shipped.
- **2024 and 2026.** Beacons with heat, fluid or burner energy (t=113632, t=132603). Won't implement: "huge performance overhead every time the amount of energy they have changes."
- **June 2026.** A spoil-time multiplier on containers (t=134525). boskid, won't implement: "Design decisions around spoilable items make features like this not possible."
- **July 2026, 2.1.12.** raise_on_crafted, an opt-in per-recipe event. Shipped; Moshine and Muluna deleted polling loops for it.
- **August 2026, 2.1.13.** local_effect, a runtime per-entity effect, replaces a hidden beacon per machine. Shipped.
- **August 2026.** Better Belt Balancer removes its compiled-belt feature after a 2.1 check breaks it: "if this API is ever implemented, I will restore the original functionality."

Each "no" is about a vanilla type growing a part, or an event firing globally. Each "yes" is an opt-in on one prototype. This proposal is built only from the second kind.

## 5. Worked examples

**Cold box, spoil add-on** (corrundum's ice box; today a container plus a 53-tick loop over every box on every surface). Shape S1 (watcher), and only with the add-on: a 16-slot storage inventory named cold with `spoil_modifier = {multiplier = 8, requires_power = true}`; an electric source at 10 kW; `activity = "inventory_not_empty"` with `activity_inventories = {"cold"}`, so it draws power only while something is inside. No control stage at all. Items entering while powered get eight times their remaining spoil time; leaving, an eighth; losing power re-stamps the 16 slots once and shows no_power. The add-on needs a stack's spoil tick to be able to go past full freshness while it sits in the declared inventory; a Lua write refuses that today (measured). If the engine cannot allow it, the add-on is dropped and nothing else changes. Honest differences: corrundum pauses spoilage below 50 percent and rewinds it above, and exempts Aquilo and Frozeta; the add-on slows spoilage by a constant factor. Pause stays reserved: the public API exposes a stack's spoil state as an absolute tick (`LuaItemStack.spoil_tick`), and the author assumes there is no not-started state to return a stack to once it is set (for Wube to confirm), so pause would be a new engine state or a periodic re-stamp that drifts; multiply maps onto the spoil tick as it is.

**Dino dig site** (pY; today an assembler shell permanently disabled by script, a hidden food container, two entities per trip, a 61-tick batch, and a mod-drawn pane for the food slots). Shape S3 (machine), keeping pY's mechanics:

```lua
{ type = "composed-machine", name = "dino-dig-site",
  energy_source = { type = "electric", usage_priority = "secondary-input" },
  energy_usage = "100kW",
  module_slots = 4, allowed_module_categories = {"digosaurus"},   -- creature slots, as pY uses them today
  inventories = { {name = "food",  role = "input",  size = 2, filters = {...}},   -- pY's food list
                  {name = "ore",   role = "output", size = 4},
                  {name = "trash", role = "trash",  size = 1} },
  process = { cycle_time = 20, consume_at = "script" },
  conditions = { {type = "module_slot_filled", count = 1, status = "no_modules"},
                 {type = "inventory_below", inventory = "ore", max_count = 1000,
                  status = "full_output"} },
  circuit_connector = {...}, circuit_outputs = "contents",
  events = { cycle_started = true, cycle_finished = true } }
-- cycle_started: eat one food, remember its yield. cycle_finished: insert yield x filled creature slots.
```

The food sits in a filtered input inventory, so it is on the wire through `circuit_outputs = "contents"`, in the machine's own window, and takes ghost requests. The cycle_started handler removes one food and remembers its yield; the cycle_finished handler picks a scanned ore as the mod does today, inserts the yield times the filled creature slots, depletes the ore, and sets blocked_status to no_minable_resources when the scan is empty. One timer stands in for up to four parallel trips; the yield scales with the creatures present. The two conditions are pY's no-creature status and its stop-at-1000 rule. Deleted: the hidden container, the shell, the loop, the error sprites, the pane, the per-trip entities. Two Lua calls per trip per site instead of a poll every 61 ticks. Since 2.1.12 a burner assembler running a token recipe with raise_on_crafted could raise the finish event, but the food slot, the yield rule, the no-creature status and the stop-at-1000 rule would still be faked around it.

**Timed converter** (the 2024 request for "a non-machine with input, output, module and fuel inventories", p=687544, unanswered for two and a half years). Shape S3: a filtered input, an output, a burner source, two module slots, a 5-second cycle with start script and consume_at script; events inventory_changed on input and cycle_finished. The first handler calls start_cycle when the mod's rule says the input is convertible; the second removes the stack it chose, inserts the result, and starts again or does not. The request's three complaints are each one field: a tick between crafts, the consumed stack with its tags, the no-craft case.

**Seep derrick** (pY; today a mining drill plus a hidden assembler for the second fluid input, a render object per run, a 67-tick loop). Shape S3 with two fluid boxes: a 2-second cycle with ingredients 10 drilling fluid and products 100 crude oil, blocking when the output is full; a fluid_at_least condition; one uint32 setting named depletion; event cycle_finished. The handler adds the cycle count to the setting, which survives blueprint and undo without a storage table, and inserts the depletion bonus. Deleted: the hidden assembler, the loop, the render object, the fluid API calls.

## 6. Implementation

The type is built from parts Wube already maintains, with a named list of new code:

| Part | Behaves as |
|---|---|
| Timer, energy source, modules, sleep and wake | the furnace's, without recipe selection |
| Named inventories, filters, bars | the container's, one per declared inventory |
| Circuit reads (contents, working, finished, read_fuel) | the assembler's control behaviour |
| Opt-in events | raise_on_crafted's opt-in; delivery queued (new) |
| **New code** | shape selection at load; drop/pickup rules across inventories (SPEC 3.5); the condition evaluator; the event queue; window layout for several inventories |

Sizing is Wube's to judge. v0 below is the smallest piece that stands alone; the GUI is the riskiest unit.

Risks in order: the GUI; inserter rules across several input and storage inventories, where the furnace's special cases live (`SPEC.md` section 3.5 fixes the order); ghost item requests on a non-crafter (whether the generic item-request-proxy path covers a non-crafter is for Wube to confirm); tick_interval, whose baseline is a countdown on the shape's list and whether a native every-N-ticks schedule can host it is for Wube to say; the point at which queued events are raised; the spoil re-stamp hooks, one on every transfer path into or out of the declared inventory (add-on only); and the maintenance commitment Rseding91 named in 2020.

### 6a. Delivery order

**v0: the machine shape alone.** One new type, `composed-machine`, that accepts only prototypes resolving to S3 (process plus an energy source) and S0 (no process, no tick-watch), which comes free because it is constructed like a container and never updated. S3 behaves as the furnace does, with recipe selection removed. The process is fixed (`cycle_time`, ingredients and products) or script-consumed (`consume_at = "script"`, `start = "automatic"` or `"script"`). The machine has 1 to 4 named inventories with input, output, storage and trash roles and the drop and pickup order of SPEC 3.5. It takes any vanilla energy source, module slots with `local_effect`, the assembler's circuit reads (contents, working, finished, read_fuel), the built-in statuses, and two opt-in events, `cycle_started` and `cycle_finished`, raised as raise_on_crafted is raised today (synchronously, unless Wube prefers the queue). Its window is the furnace window with one grid per inventory, capped at 4 inventories and 256 slots. That alone covers the dig site, the hearth (activity = always), the timed converter, the creep collector and the seep derrick, and it gives S0 multi-inventory stores with real inserter rules. It touches no shared transfer path and no vanilla type.

The built-in statuses include the two conditions the dig site needs, `module_slot_filled` and `inventory_below`, because they map onto the existing no_modules and full_output statuses.

**Deferred**, each as its own separately refusable step:

- the S1 watcher and S2 timer shapes;
- `tick_interval`;
- conditions beyond the built-in statuses;
- settings;
- script circuit outputs;
- fluid thresholds;
- the `inventory_changed`, `power_state_changed` and `status_changed` events;
- the deferred event queue;
- the spoil add-on.

## 7. What the Lua reference mod demonstrates, and what it cannot

The reference mod, component-lab (`mod/component-lab/`; its state is in `STATUS.md` there), builds the sixteen test entities of `docs/ENTITIES.md` and `docs/TEST-ENTITIES-2.md` with the nearest native shells and hidden parts, so the benchmark measures the status quo exactly and brackets the native type from below. It demonstrates faithfully: every S0 shape (a container with filters and a circuit connector is exact); the process with cycle_finished, because an assembler shell with a fixed_recipe and raise_on_crafted is the real crafting-machine timer with native progress, animation, power draw and status; engine-side ingredients and products, as the shell's real recipe; start = "script" through disabled_by_script, one tick late; modules; script output through a hidden constant combinator; a continuous burner through a hidden reactor. It exhibits the blueprint, undo, cut-paste, clone and mining failure modes, with the handlers' cost measured separately. The second eight entities and their measurements are in `docs/TEST-ENTITIES-2.md`, `bench/RESULTS.md` section b and the README; how they were added is in `CHANGELOG.md`.

It cannot demonstrate: a watcher at near-zero cost per tick (no power-state event, so the cold box polls); coalesced, ordered, engine-raised inventory, status and fluid events (all polls); sleeping at crafter cost with wake on transfer (nothing tells Lua when to re-enable a disabled entity); several inserter-reachable inventories without a proxy container per inventory; per-transfer spoil stamping with a correct unstamp on every exit path (there is no transfer event for automation, so a stack leaving by inserter or loader keeps its slowed timer; hand removal can be caught through the player inventory events, at a cost on every player; the emulation's periodic scan over-counts the add-on's cost); blocked_status and status-driven visuals without render objects; tick_interval; any whole-entity lifecycle without Lua. For each, the benchmark reports the Lua column as the ceiling and marks the native number "not reproducible in Lua", projected from the native comparison times D over A.

What is still open and matters here, as questions for Wube rather than claims: whether a native every-N-ticks schedule can host tick_interval, or the countdown baseline is used; whether an entity can change how often it updates at runtime; what wakes a crafter that slept with no drop target; whether every inventory transfer path (script inserts included) passes through one post-transfer notification; whether product delivery always runs serially; for the spoil add-on, whether a spoil tick may pass full freshness inside the declared inventory; how mining drills, inserters and boilers draw energy; and whether a script active = false detaches an electric source from its network.

The cost is the smaller half of the argument. The dig site's emulation runs on events already and costs 60 ns against 47; what it lacks is everything a real entity has by being one entity. Checked against the 2.1.24 API reference, the reference mod's test suite and the mods' own source, today's workaround cannot: (1) be read on a wire, because the wire reaches the shell and the food, fuel or fluid that matters sits in a hidden entity nobody can select (the suite's "wires cannot read the food" test: a wooden chest on the same red wire reads its copper, the shell reads nothing); (2) keep every slot in the machine's own window: this is possible but a second panel, since a mod can dock a pane beside the vanilla window (LuaGui.relative) and, since 2.1.7, show a hidden inventory's real slots in it with engine cursor handling (the `inventory` GUI element), but the pane sits outside the machine's own status and fuel bar and script rebuilds it each time the window opens; (3) show its status and diode from its parts the tick they change, since custom_status is a string the script writes at its next poll, up to 61 ticks late; (4) burn fuel as fuel on a type without a burner: no fuel bar, no no-fuel status, no inserter top-up rule, no fuel request on a ghost, nothing on the wire (51 prototype types take an energy source; container is not one), which is why the hearth needs a hidden reactor; (5) give inserters per-slot rules, since a proxy container exposes its inventory both ways and a proxy fuel door fills to a whole stack; (6) have robots fill a ghost's hidden-part requests: boskid disabled ghost item requests through proxy containers on purpose (forum p=685891, 2025): the proxy's cross-entity indirection was never verified in GUI and blueprint code. A composed machine owns its inventories, so there is no indirection; (7) survive blueprint, undo, upgrade planner and cloning without a library recreating the hidden parts on every path, which "mostly" works (p=655527); (8) turn, glow and smoke as one thing: every rotation must be mirrored onto each hidden part by script, and the light follows the hidden reactor's fuel rather than the machine's work; (9) sleep when idle: a shell can leave the update list with disabled_by_script, but nothing tells Lua when to re-enable it, so a workaround either polls or stays awake, and a recipe-less shell left enabled costs 18 ns per instance doing nothing (the storehouse, measured); (10) appear once in the power graph, the statistics and the tooltip: a creep collector's script can debit a hidden energy interface per tile (`LuaEntity.energy`), but that interface is a second consumer in the power graph with no status of its own, and it has to be polled to know when work can resume; (11) be told when something happened, since no inventory-changed, power-state, fluid-threshold or script-consumption event exists among the 229 events of 2.1.24, and an inserter or loader taking a stack out of a box raises nothing. The composed type has every one of these by construction, because the parts are its own.

## 8. Beyond v1: the parts that would extend the game

v1 converts 22 of 189 surveyed scripted buildings fully and 36 partly; most of the rest need a different core (inserter, roboport, train stop, silo, unit, drill), which this type does not claim. What is left is parts, and `docs/V2-PARTS.md` ranks them by the rows each one lifts on its own. Its revision 1 dropped seven buildings and three parts that were already buildable in vanilla 2.1 or had no existing engine mechanism behind them (the dropped list is in `V2-PARTS.md` section 1). Every kept part obeys the four v1 rules: fixed at load, off the list when idle, no Lua in the update, wrapping something that exists.

In the same release, a few hundred lines each, none copying another type's update: triggers on cycle start and finish (the projectile, smoke and area-effect machinery weapons use, with the entity as source; script effects forbidden there because a script trigger effect is assumed to raise its Lua in place, for Wube to confirm), which gives Renai's item cannon and SE's delivery cannon with no Lua; typed settings (item, fluid, signal, quality, and an entity-relative offset) that become blueprint parameters the way the constant combinator's signals do today, retiring the prototype-per-value pattern (RealisticReactors keeps 250 reactor prototypes, t=113731); a wildcard ingredient for sinks (three mods generate a recipe per fluid); and small fields: emissions per cycle, the light, destroy-on-empty, fluids in the contents read, editable sections.

In a second step, 1.1 to 1.7 thousand lines, the parts that lift the most rows: electric generation as the electric energy interface's production side filled per cycle or, with a burner, fluid or heat source, in the form of the burner generator, which already pairs a burner with an electric output (one electric source per entity is assumed, so electric in and electric out stays out: 16 sole rows, 12 of them mods, the pY solar family first); heat output as the reactor's heat buffer, filled by the owner in its own update, with conduction left to the heat-pipe update, assumed to charge the owner nothing (7 rows, five of them Cerys); a circuit enable condition through the enable/disable circuit condition every pump and inserter has, and signal-bound settings pulled by the entity at cycle start, never written from the control behaviours' update, which is assumed to run separately from the entity update (5 rows); and products from the tile or the surface property table plus placement on resources (5 rows). With those, FULL is at least 64, or 68 counting the four two-blocker rows both of whose blockers ship.

Debated, for a third step: a logistic role per inventory, which is the logistic-member behaviour ten types, eight of them not chests, already have and the thing boskid's refusal of logistic proxy containers argues for (an owned inventory is notified of its own changes, t=136024); and effect broadcast, which would change beacon reception, which today only crafters, labs and drills have, and which `LuaEntity::local_effect` (2.1.13) has already made unnecessary for the per-machine cases.

Dropped: a solar-curve generation form (solar priority is SolarPanelPrototype-only and the vanilla panel with solar_coefficient_property already is a tide mill), a continuous process mode (the vanilla boiler takes the full energy-source union and converts through output_fluid_box), two heat buffers or two electric sources on one entity, a status event on passive shapes (a container cannot be frozen and has no update), a surface-typed setting, and a runtime resource condition nothing re-evaluates.

What that buys players, as buildings that become one prototype (`V2-PARTS.md` section 3, each one prototype and at most one handler): with v1 alone, a hearth that burns whether or not it crafts (t=61277 and t=108882: today a hidden reactor and a tick loop), a greenhouse gated by daylight and fed by heat, a radio mast, and a powered-state alarm block (asked since 2014); with the spoil add-on, an aging cellar and a smokehouse (per-container spoil rates, the part boskid refused for containers in 2026). With the parts of the same release, a kiln that burns anything and belches per cycle. With the second step, a slag generator (power from a fluid with a solid byproduct, t=120072), a blast furnace that heats a pipe network while it works (t=130444), a reactor whose output is a signal-bound setting, products that depend on the tile, and a furnace tuned by circuit. The open questions for the engine team are in V2-PARTS.md section 5.
